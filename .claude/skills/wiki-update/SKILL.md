# Update the tibo.dog wiki

The wiki is generated by `node build.mjs` from data dumped out of the deployed game. `origin/main` is canonical. The Amp monitor dispatches update workers; the legacy pcstyle systemd timer is disabled. Do not require SSH, re-enable the timer or copy another machine's checkout over Git.

This tracked file is the canonical repo-local **update wiki** skill: `amp skill info wiki-update` must resolve to `.claude/skills/wiki-update`. Preserve that registered name/path rather than installing a duplicate. Whenever you discover or correct a method, update this skill in the **same cycle** as the implementation/evidence, validate it and reload skills. Load `building-skills` before managing SKILL.md; never edit server-synced global caches. Validate discovery with `amp skill info wiki-update`, frontmatter/name, referenced commands, and the affected checks below. Keep actual bundle names in evidence/data, not this reusable procedure.

## 1. Find the real state

- Run `node tools/freshness.mjs` on start/resume. It diagnoses git/game/deploy drift; it never authorizes resetting or overwriting files. The resume hook is read-only and a timeout is not a successful check: run it explicitly again before delivery.
- Fetch `origin/main`, inspect local changes, and fast-forward/rebase only when safe. Preserve concurrent edits; never force-push, reset hard, or stash/discard someone else's work. Unshallow the relevant history before interpreting missing commits or widespread add/add rebase conflicts.
- If local refs, production or the live game are confusing, find same-repo active/recent threads from the last 24 hours, read their work and `Amp-Thread-ID` commit trailers, and contact the actual owner before changing state. Coordinate with the monitor rather than starting a competing worker. Do not retry or unarchive an archived coordinator.
- Live wiki build: `curl -fsS --max-time 25 -H 'Cache-Control: no-cache' https://tibodog-wiki.vercel.app/api/live-build`. Compare its documented/current build with `data/build.json` and the live game's entry script.
- List every `unreviewed` entry in `data/builds.json`. Older unreviewed entries can sit behind a reviewed one, so check the whole list, not only the latest entry.

If the live game build is newer than `data/build.json`, run `bun run game:update` (or `bun run game:check` to look first).

If a previous worker already applied this build, recover its uncommitted patch, report and mirrored assets through thread file-transfer tools. Continue that review; do not reapply with `--force` and replace the original diff with a self-comparison. The updater reports `needs-review` until all pending history entries are reviewed, even if the live and documented build names match.

## 2. Review the diff since the last deployed build

Review from the last build that is live on the wiki to the current one, plus any older unreviewed builds. The per-build reports are in `.cache/<main>/report.md`.

`.cache/` is local and Git-ignored. Preserve/transfer the relevant old and new assets, extracted data and report when handing off an unfinished update. A fresh orb will not have them. Try existing mirrors before the CDN: old hashed files can return 404. Missing assets for the actual comparison are a review limitation, not evidence that game logic is unchanged.

Use thread file-transfer tools for patches/archives, not messages containing paths or commit IDs alone. Transfer both builds' own assets, data, atlases, original updater report, review/probe scripts and outputs; record archive size/SHA-256, source thread and exact revisions. Verify the digest before use. Keep the original report and measurements when resuming; append review findings separately. Download private attachments with `amp files get <url> -o <directory>/`, retain the chosen unique filename and read the complete export. Never use unauthenticated curl for Amp attachments.

```sh
node tools/diff-data.mjs .cache/<old main>/data .cache/<new main>/data
python3 -I tools/code-diff.py .cache/<old>/assets/sim-*.js .cache/<new>/assets/sim-*.js 60
python3 -I tools/code-diff.py .cache/<old>/assets/boot-*.js .cache/<new>/assets/boot-*.js 60
```

Config objects can move between the sim and boot chunks. `diff-data` then reports them as `no match in new build` and `new export` instead of diffing them. Match old and new objects by their keys and compare them yourself.

If `bun run build` fails with `config object with keys ... not found`, look at `cfgBy` in `lib/data.mjs` first.

### Review every module using each build's own assets

The updater's sim/boot report is a starting point, not a complete review or permission to call a build unchanged. Inventory all JavaScript modules, added/removed chunks and stylesheets; include both mount/choices variants, duplicate basenames, workers, worklets/implementations/wrappers and every localization. Pair duplicate chunks by imports/exports and responsibility, not whichever filename a basename map retained. Record counts, unmatched roles and source limits.

Follow moved responsibilities into new/lazy modules. Separate consistent identifier/asset/build-metadata renames from statement changes, and inspect changed executable code in context. Compare each build with its **own** sprite tables and PNGs: using the new table against an old PNG gives false art differences. Check retained frame crops and wiki icons, not just repacked atlas hashes; distinguish changed pixels, packing and sampling/rendering behavior. Verify dormant flags and their actual callers before describing inactive code as gameplay. Never infer “no gameplay change” from identical registry/config alone.

For a metadata-only candidate, strengthen generic hash-normalized diffs with an exact **mapped-dependency** check: replace each old asset filename with its paired new filename and only the known own-commit literals, then compare complete modules. Generic `CHUNK` placeholders can hide a swapped dependency. Prefer statement-level diffs to expensive character-level SequenceMatcher runs on large minified chunks. `fetch-build.mjs` mirrors JS/atlas PNGs, not all CSS: collect stylesheet references from each build's own index and modules, fetch those exact named files, record their digests and compare them explicitly. A missing local stylesheet is a mirror limitation, not evidence the game removed it.

When identifier churn prevents exact equality, retain that failure list. A binding-aware AST comparison can separate local renames from changed statements while preserving literal values, static property names and exact mapped import paths; compare import bindings by use, not their declaration order. Treat moved imports as review findings, follow their producers and callers, and inspect residual changes rather than reporting a generic normalized match as exact equality. For rendering caches, probe asymmetric velocities, unchanged reads, changed components, recycled pool IDs and zero speed; for lazy effects, check the actual attachment caller, idempotence and audio's hazard reference. These isolated probes do not measure frame rate or prove every browser path.

An AST consumer match is not enough when a producer's export aliases change. Resolve each used old export to its producer binding, map that binding to the new producer, then check that the new consumer imports that same binding. Preserve noncomputed property keys even for shorthand properties; preserve side-effect imports and source ordering. Report unsupported namespace/re-export/default cases and unmatched statements as residuals. Align inserted top-level declarations without treating positional shifts as semantic equality; inspect all residual executable changes, including procedural sprite generation outside atlas PNGs.

### Play the new build

Load the `playing-tibo` skill and play the new build, not just its diff:

- Smoke test: `node tools/play.mjs --build <new main> --minutes 5` must finish and report damage from several weapons. If it cannot find `Game`, the stat enum or the recompute function, fix the lookup in `tools/play.mjs` as part of this update.
- For every changed weapon, item, boss, event or formula the diff shows, write a short scenario that measures the change on the old and new builds with the same seed and inputs. Keep the numbers in your report. A change you cannot reproduce in a run is not explained yet.
- Compare the smoke with the old build too when claiming unchanged behavior. Exercise the changed branch with actual simulation/controller code and asymmetric inputs, boundaries and controls; examples include difficulty variants, timers, target/capacity rules, returning/orbiting shots, late-game phases and cross-tab settings. Derive expected values independently. Record seed, inputs, durations and numeric results, and distinguish isolated adapters/forced scenarios from naturally acquired gameplay. Check byte/identifier-normalized code where probes cannot cover every path.
- Check lazy rule installation before measuring optional sim hooks. The browser controller installs its own build's `RUN_EXTRAS.rules` through `useRules` / `installLegendary`; a bare headless Game may omit behavior such as bullet hatching. For those probes, import and install the original rules from each matching mirror, exercise the real sim tick and callback, and retain a no-rules control. Do not implement a substitute callback or claim an unchanged general smoke exercises that branch. For owner-linked splits, test timing on both sides, asymmetric directions, inherited fields, dead/hidden/recycled owners and full/partial pools; pool iteration order is not angular order.
- Keep limits honest: client replay submission is not server replay validation; draw cadence is not physical battery/temperature measurement; Chromium narrow viewport is not a real phone; missing original assets are not a successful historical check. No gameplay update or five-minute replay is required solely for journal/prose changes on an unchanged game build; state that scope rather than inventing fresh gameplay evidence.
- When a run settles an open question on `/coverage`, update that page in the same change (see the skill).

## 3. Fix the pages

- `bun run game:update` also refreshes `data/changelog.json` with `tools/dump-changelog.mjs`; **In-game journal changes** reports additions, removals, revisions, kind/target/message metadata, ordering and date/code regrouping with both sides. Stable IDs are preferred; old notes use message IDs, so a changed legacy ID can appear as remove/add. Same-build checks compare the saved journal and source digest without overwriting pending review reports. If the extractor throws, fix its code-shape lookup and regression fixture, not the generated JSON by hand. For a journal-only repair on the same build, regenerate with `node tools/dump-changelog.mjs <assets> <main> data/changelog.json`; do not force-reapply gameplay data.
- The dated literal can be assigned directly or passed to a display-grouping function. Keep extraction fixtures for both shapes. Inspect and probe any wrapper with adjacent equal dates, different dates and a nonadjacent repeated date; do not mistake a grouping-code change for new notes. Verify that extracted date groups match the rendered groups; if the source actually contains duplicate dates, follow its grouping function rather than publishing raw duplicate cards.
- Verify the official live **What's new** UI using `browser-use` / `using-agent-browser`: current-version/unversioned group **and all collapsed older days**, with full ordered text, date/code groups, counts and kind icons. Match extraction to a supplied full export when present. The unversioned list is sorted by the game's own comparator; declaration order is not display order. Record source build/chunk/URL/SHA-256 and actual browser-check date/build separately: regenerating data is not a new browser check. If WebGL 2 is unavailable in the orb browser, diagnose it and try Chromium's software ANGLE/SwiftShader flags consistently across the session; do not bypass a website safety warning or claim a blank/error screen verified the journal.
- Audit journal history against existing build comparisons, code and measurements, not by replacing them. A matching short code is a cross-reference, not proof of one-to-one introduction; unversioned notes may combine several observed builds, and older notes can be revised or regrouped later. An omission does not prove removal; “freeze” or “faster” shorthand does not override measured rules. Keep publication dates distinct from UTC observation/deployment times and do not infer the journal timezone from deployment times. Preserve older findings and disclose unresolved conflicts/missing assets. Revisit stale “No announcement found,” first-fix, language-date and exhaustive-balance claims when official notes contradict them. Keep the audit and limitations in `data/journal-audit.md`, rendered on History.
- It also refreshes `data/i18n-names.json` (every entity's name in the other 26 languages, and the language list on /controls#languages) with `tools/i18n-names.mjs`; the report's "Names in other languages" section lists retranslated names, and a changed language list needs review of /controls#languages.
- Tables built from `data/` update on their own. Check prose that hard-codes numbers or names: difficulty notes, POI text, controls, revive and stat notes in `pages/*.mjs`.
- Every quote has to point at the file that contains it. Use `cite(SIM, ...)` or `cite(BOOT, ...)` accordingly.
- Check `data/prose/` as well as `pages/`: exact named source files take precedence over same-prefix wrappers. A quote moving between boot/sim/lazy chunks needs its source label repaired even if the text is unchanged. Do not weaken or broaden the checker to hide an unresolved quote. Verify the language list, all translated entity names and relevant UI wording; don't claim complete translation testing from English-only checks.
- Verify all current/changed citations against the matching mirrored build. `data/mechanics-notes.md` is an archival snapshot of the original build, intentionally excluded by `check-quotes.mjs`; preserve it unchanged during routine updates. Do not relabel its quotes as current or claim its game data is still identical. If its deleted original assets cannot be recovered, disclose that historical quotes were not reverified; this alone does not block an otherwise verified current-build update. Changes to archival claims require their own evidence.
- `pages/notes.mjs` strings are template literals, so escape backticks as `` \` ``.
- Text about past builds belongs in `data/builds.json`, never in `pages/*.mjs`, because the updater rewrites chunk names there.

Then rebuild and check the quotes until nothing is unresolved:

```sh
bun run build
node tools/check-quotes.mjs .cache/<new main>/assets --write
bun run build
node tools/check-quotes.mjs .cache/<new main>/assets
node check-middleware.mjs
node --test tools/*.test.mjs pages/*.test.mjs tools/detector/*.test.mjs
git diff --check
```

`--write` only fixes quote text where it appears verbatim in source; check moved chunk labels and unresolved quotes by hand. Run checks as separate commands or join with `&&` so a later success cannot hide an earlier failure.

## 4. Write the history

For each unreviewed build, set `status: "reviewed"` and replace `changes` with a short, player-facing summary. Before you attribute a change to a build, check that build's `.cache/<main>/data`, because a cumulative diff hides which build introduced what. Write the file with `JSON.stringify(a, null, 1)` to keep the existing format. Right before you deploy, set `updated` to the current UTC time (`new Date().toISOString()`, seconds precision) on the newest build's entry and in `data/build.json`; the site shows it as "data synced" and in the Wiki updated column on `/versions`. Rebuild and confirm that `dist/versions.md` has no "Not reviewed yet".

For a historical/journal-only audit, preserve the original gameplay sync/observation timestamps and measured old/new results; the new wiki deployment has its own commit/time. Store historical names/claims in data, not mutable current-source labels in page templates. Browser verification prose must name the build/date actually checked rather than dynamically inheriting the next build's metadata.

## 5. Commit, deploy, verify

1. Recheck the live game build and `origin/main` before delivery. Stop on a new build or conflicting concurrent edits; do not overwrite them.
2. Ordinary coherent checked commits, pushes to `main` and production deployments of **this wiki** have standing authorization in root AGENTS.md. Commit/push often; before **every** push fetch again, safely rebase your own commits onto fresh `origin/main`, and rerun `node build.mjs`, the matching-assets quote check (0 unresolved), `node check-middleware.mjs`, `node --test tools/*.test.mjs pages/*.test.mjs tools/detector/*.test.mjs` and `git diff --check`. Do not hide a failing command behind a later success. Subscribe to CI for the exact pushed full SHA with `amp.create_github_subscription` and fix failures caused by the change. This authorization does not extend to unrelated infrastructure or bypassing tool approvals.
3. Use one delivery owner. Check whether the push already triggered the correct Vercel deployment before starting another. Verify project `prj_ezw3MZfNGIIQlXJSKRbpzexA2qtp` / team `team_ceF7ek1jhDCXPvwYHv5HrsGM` maps to `tibodog-wiki`. Use available connected tooling or load `vcx` before the CLI; a Mac/SSH connection is not required.
4. Deploy only the tested pushed SHA, not a drifting branch or dirty local upload. Wait for Vercel **READY**, verify its full source SHA and production alias, then fetch `origin/main` again and compare production `/api/index.json` `meta.wiki.commit` with that latest full SHA. Check `/sources` current entry, `/versions` with no pending builds, `/api/live-build` up-to-date, the actual live game's entry and every changed page. A push, READY without alias parity, or cached HTML alone does not mean live completion. Coordinate if main/game advanced rather than overwriting the newer owner's work.
5. Render affected desktop and narrow states; inspect screenshots and DOM/overflow checks. Use real mobile/touch emulation only when needed and state its engine/limits. Capture and inspect a short real-pointer clip for changed interactions, including neighboring controls. Save reviewable evidence under `.amp/in/artifacts/`, scratch elsewhere. If a recording fails, report the loss and recapture a shorter/lower-rate sequence rather than claiming the lost clip verified behavior.
6. `vercel promote` or a rollback turns off automatic production aliasing. Promote the next good deploy explicitly if needed.
